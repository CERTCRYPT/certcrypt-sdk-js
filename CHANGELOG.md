# CHANGELOG

This package follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries are one line per change: `type:scope: what changed`, where `type` is
`feature`, `bugfix`, `breaking`, `deprecation`, `security` or `docs`.

## 1.0.0

* feature:Settlement: `VerificationPackage` has the closed member set of verification-package/1 — `base_certificate` and `verification_context` always present — which is what an offline verifier in package mode accepts
* feature:Consistency: `assembleContextSnapshotCertificate` mints a CCVP/1 context snapshot certificate (`payload.snapshot` plus one `subject.context-snapshot/1` subject committing to it, shape and profile preconditions checked before signing); `assembleBaseCertificate` takes an optional `context` (the snapshot issuer by `signer.id` and composite key fingerprint, and the `context_set_id`); `issuerKeyFingerprintHex` gives that fingerprint. Held to the `ccvp-consistency` vectors and, end to end, to the verifier toolkit's `verifyConsistency`
* security:Issuance: `subject.ai-decision/1` accepts one bounded decision record with a canonical decision id, one declared model, an explicit client/runtime observation boundary, real UTC millisecond timestamps, and ordered multimodal input/output parts; every part has a globally unique id and nonce, a lowercase MIME essence, an admitted profile and a salted CCCP commitment, while parameters and context remain bounded flat string maps
* feature:Issuance: `buildAiDecisionSubject` generates independent part nonces, computes profile-aware commitments, validates the complete decision record and returns the subject plus private opening material; `buildAiDecisionPart` provides the same operation for one part
* security:Issuance: the material of the JSON subject profiles (`subject.collection/1`, `subject.ai-decision/1`, `subject.context-snapshot/1`) is parsed strictly: a member name repeated in any object, at any depth and after escape decoding, refuses the subject before it is canonicalized, so no certificate commits to material that two readers would read differently. Held to the new conformance family `strict-json`
* security:Node authentication: the issuer proof signs `certcrypt:issuer-auth:1|<challenge>|<host>|<METHOD> <path?query>|<sha3-256 of the body>` (`issuerAuthMessage`), so a copy is good only for repeating that very request. `NodeClientOptions.issuerAuthProof` receives the request (`IssuerAuthRequest`: method, url, body)
* feature:Retries: every attempt of a read carries a newly minted issuer proof, because the node refuses a challenge it has already accepted; a retry of a read that reached the node is therefore never refused as a replay
* feature:Cryptography: the ECDSA P-256 component is RFC 6979 deterministic — SHA3-256 prehash, nonce from HMAC-SHA3-256, low-s, raw `r||s` — so the same key over the same message always yields the same signature. Computed with `@noble/curves` 2.2.0 (with `@noble/hashes` 2.2.0, both pinned exactly), because `node:crypto`'s `sign` draws a random nonce. Held to the new conformance family `ecdsa-p256-deterministic`. The ML-DSA-65 component stays hedged
* security:Issuance: the issuer's signing key depends on the seed alone — P-256 from `SHA3-256(seed || "issuer-cert-key/p256")`, ML-DSA-65 from `SHA3-256(seed || "issuer-cert-key/mldsa")`; `issuerKeyId` is a label that never changes the key, and its default is `"issuer:" + keysetRoot[0:32]`. Held to the new conformance family `issuer-key-derivation`
* security:Exports: no single-component signing primitive is exported (no standalone ML-DSA-65 or ECDSA P-256 key generation, signing or key conversion): a caller cannot produce a signature without its post-quantum half
* feature:Exports: `deriveIssuerKey`, `computeExpiresAt`, `resolveCollectionSubjects`, `buildCollection`, the digest helpers (`digestBytes`, `digestHexBytes`, `digestHexText`), the JCS helpers (`jcsCanonicalizeBytes`, `jcsCanonicalizeString`), `SUBJECT_CONTEXT_SNAPSHOT`, and the types `SettlementPreferences`, `CollectionLeafInput`, `BuiltCollection`, `ResolvedCollection` and `MemberResult`
* feature:Issuance: a `poolId` learned at activation reaches the commitment, so an issuer configured without `poolId` can issue. `mintVerifiableCertificate()` takes an optional `poolId` and refuses one that differs from the client's own
* security:Issuance: `mode: "unlinkable"` without a `leafStore` is refused at construction: an in-memory store would restart at zero and reuse every leaf
* feature:Issuance: `commitmentTtlSeconds` must be a positive whole number of seconds, checked at construction
* feature:Issuance: `resolveEmission()` reports every terminal state other than `independent_ready` and `expired` as `rejected` — `insufficient_capacity`, `replay_detected`, `pre_evaluation_rejected` and `submission_failed` included — so no terminal state resolves as `pending`. The same holds on the by-commitment fallback
* feature:Issuance: `resolveEmission()`'s `verificationContext` is optional and defaults to the instance's `rulesVersion` and `systemId`
* feature:Recovery: `listUnresolvedEmissions()` activates first, so a process that never emitted sends a signed read
* feature:Node client: `health()` returns `false` on a transport failure rather than throwing, and gives up after 30 seconds
* feature:Node client: every request (submit, activate, reads, health, redrive) is bounded at 30 seconds (`REQUEST_TIMEOUT_MS`), and every read (`getOperation`, `getEmissionByCommitment`, `listUnresolvedEmissions`, `listDeadLetters`) is retried under the `transport-retry` policy and the `retry` options, as a submit is
* feature:Node client: a 2xx submit whose body is not a JSON object is a transport failure, retried with the same `request_id` (`issue failed: unparseable node response`)
* feature:Node client: an activation refusal names the node's code and message (`activate failed: HTTP 409 — integration_key_replaced: …`) and carries `retryAfterMs`
* feature:Settlement: `waitForOperation()` runs on the client's clock (`clock`), one request per poll; an exception thrown by `onProgress` is swallowed, and a sleep of ten seconds or more, or an overdue window, is announced with `console.info` when no `onProgress` is given
* docs:Issuance: `prepare()` checks, in order: activation, pool, holder, root fingerprint, system id, subjects, subject profiles, then TTL. An optional value falls back only when absent: an explicit `0` or empty string is used as given
* security:Activation: an activation answer is read fail-closed, in order: not a JSON object (`activate returned no JSON object`), a required field absent or empty (`activate returned no …`), a field of the wrong type — `level1_binding` not an object, `level1_signature` not a composite signature, `holder_id`/`pool_id` not strings (`activate returned a malformed …`), or a `status` other than `redeemed`/`already_consumed_same_root` (`activate returned an unrecognized status`). Each throws `CertcryptNodeError` with no HTTP status, and nothing is cached or persisted. `CertcryptNodeClient.activate()` returns the new `ActivationResult` type.
* security:Activation: a `POST /v1/activate` answer that is not a JSON object, or lacks `level1_binding`, `level1_signature`, `holder_id` or `pool_id`, throws `CertcryptNodeError` (`activate returned no …`) and nothing is cached or persisted, so no binding is left with undefined halves or an undefined `holderId`
* feature:Issuance: `Certcrypt.issue()` — the single issuance surface: derives the signing key from your seed, canonicalizes each subject byte-identically to the verifier, computes the commitment, mints the signed `base_certificate` and submits the issuance, returning the certificate and an operation identifier
* feature:Issuance: The `Proof of Independence` does not exist at issuance time — it is obtained later, once the operation settles
* feature:Issuance: No opaque-digest mode — a certificate always commits to real content, so a third party can bind the proof to those exact bytes
* feature:Issuance: Multi-subject certificates under one signature; order is significant and `subjects[0]` is the primary face
* feature:Issuance: Six subject profiles — `subject.binary/1`, `subject.text/1` (line endings normalized to CRLF), `subject.email/1` (RFC 5322 header-unfolded), `subject.collection/1` and `subject.ai-decision/1` (canonicalized by value under RFC 8785 after a string-only precondition, so key order stops mattering), and `subject.context-snapshot/1` (canonicalized by value after its no-JSON-number precondition)
* feature:Issuance: `issue()` always emits `independent-capable`, which requires the participation reference — the omission cannot be repaired after issuance, so it is not a per-call choice. `issued-only` is reachable through `nodeClient()` for a caller that deliberately wants it
* feature:`EmissionHandle`: A serializable operation handle — persist it and `resolveEmission()` finishes the job after a restart or in another process, without re-emitting; exactly one node operation per certificate
* feature:Cryptography: Composite PQ/T signatures under the CERTCRYPT Composite Signature Profile — ECDSA-P-256-SHA3-256 (classical, first; order is load-bearing) AND ML-DSA-65 (FIPS 204), each over the same domain-separated message, valid only if all components verify
* feature:Cryptography: The signing key never leaves the process — derived deterministically from the 32-byte seed, domain-separated from the operation-key tree; a KMS-backed key can be injected instead
* feature:Zero-data: `capacity.evidence/1` projects stable identifiers to operation-scoped pseudonyms, and only the projected commitment is signed
* feature:Node auth: Zero-trust authentication — a different axis from `zero-data`, which is about content. Each request carries a self-verifying proof the node checks offline with no token lookup, built from the Level-1 binding, a leaf disclosure and a possession signature over a fresh challenge
* feature:Node auth: Reads sign the exact resource being read, so scope derives from who signed rather than from whoever transported the request
* feature:Node auth: The node is a transport. The SDK activates and submits through it and asks it for nothing else — no identity proof, no pinned key. A node that is not recognized gets nothing admitted, and one that misbehaves can delay or drop a submission but never forge or alter what is signed: the certificate is signed here, and the `Proof of Independence` that comes back is signed by the CERTCRYPT System Domain, which any verifier checks offline with the verifier toolkit
* feature:Node client: Submission sets bounded at 64 members (`MAX_SUBMISSION_SET_MEMBERS`). `Certcrypt.submit()` and `CertcryptNodeClient.issue()` / `issueCommitments()` refuse more than 64 commitments with `SubmissionSetTooLargeError` before anything is sent; `assertSubmissionSetWithinBound()` is exported for a caller that groups commitments itself. A fail-fast guard, not a security boundary: the node and the submit endpoint reject an over-cardinality set fail-closed regardless
* feature:Node client: Idempotent retries with exponential backoff and full jitter, reusing the same ULID request id, so a retry never re-signs and never double-submits; terminal verdicts fail fast
* feature:Node client: Retries follow the `transport-retry` policy — a node's `Retry-After` (a restart, an outbox it cannot write) is waited out exactly, clamped to 1 s – 15 min, and never counted as an attempt; retrying ends on a time budget (`retry.maxElapsedMs`, default 120 s) with no attempt limit unless `retry.maxAttempts` is set; a 4xx other than 408/425/429 is returned at once instead of retried. `CertcryptNodeError.retryAfterMs` carries the node's requested wait when the client gives up
* feature:Node client: `pre_evaluation_rejected` is final and not retried — the node sends it with HTTP 200 and the same set always gets the same answer
* feature:Node client: `listDeadLetters()` and `redriveDeadLetter(requestId)` — the submissions the node stopped retrying (a refusal about the request or its credentials, never an outage) and how to put one back once the cause is fixed; the same signed set is resent, nothing re-signed
* feature:Node client: A member the node delivered late (`accepted_for_retry` at submit) keeps the operation id it was given; the first read that reveals its upstream id hands it to the issuer, so later reads sign the id the server routes on
* feature:Node client: Activation is invisible — the first `issue()` activates on the way past, `activate()` exists for when the deploy and the first certificate are far apart, and a cold restart needs nothing persisted
* feature:Settlement: `pending` is the normal state of a fresh emission — settlement batches many operations into one window, so the handle is a durable reference to the operation precisely so you need not block on it
* feature:Settlement: `pending.settlementWindow` surfaces the node's expected window (`window_profile`, `window_profile_version`, `target_close_by`, `expected_settled_by`) plus `overdue`, so an issuer can tell "settling normally" from "the settlement layer is stuck"
* feature:Settlement: `SettlementWindowEstimate.expected_settled_by` (and `UnresolvedEmission.expectedSettledBy`) carry the operator's estimate of when the window's settlement is anchored and final — never earlier than `target_close_by`, present exactly when it is, operational only. The wait checks twice before `overdue`: 60 % of the way from `target_close_by` to that instant, then at that instant plus one second, each pushed back by a random 0–1 s so the operations of one window do not ask at once; `overdue` (on `WaitProgress` and on a `pending` resolution) is true only once it has passed; the progress message names the expected instant, and an overdue one says settlement is past the operator's expected instant. Without it, the wait sleeps until `target_close_by` plus three seconds and `overdue` follows `target_close_by`
* feature:Settlement: The wait schedules on that estimate instead of polling — sleeps until the expected settlement instant (or, without one, the window's close) and checks once on arrival, falling back to capped exponential backoff with no estimate. `maxWaitMs` bounds the wait by wall clock; `intervalMs`/`maxAttempts` select fixed-interval polling
* feature:Settlement: `WaitProgress` distinguishes `queued` from `finality_pending` — waiting BEHIND a window and waiting ON the chain are different waits, and only the first one a window schedule can shorten. Once settlement is on the substrate what remains is its irreversibility, so a message blaming the window there points at the wrong place
* feature:Settlement: `onProgress` reports each tick with a ready-to-log `message`, and the SDK announces a sleep of ten seconds or more on the console rather than going quiet — a multi-minute sleep is indistinguishable from a hang
* feature:Settlement: The window carries scheduling information and nothing else — no amount, no capacity figure, no receipt line, no billing multiplier. An operation cost in the clear would let an issuer's operations be correlated over time, and once such a value travels in a response it lands in logs and billing records
* feature:Settlement: Window profile names are versioned values of the rules domain, published in its public rules; schedule on `expected_settled_by` (or `target_close_by`) and pin nothing to `window_profile`
* feature:Verification: `resolveEmission()` assembles the full `verification-package/1` from the handle, deriving the commitment inclusion proof locally with the same Merkle primitive a verifier recomputes
* feature:Verification: This SDK produces and assembles, it does NOT verify — it checks no signature on the artifacts it receives back, which is the verifier toolkit's job and a separate always-required step
* feature:Byte contracts: Parity pinned by the published conformance vectors, with the traps documented where they bite — hex strings concatenated as ASCII and never decoded, ML-DSA signing with an empty context and no pre-hash, RFC 3339 without fractional seconds, and leaf preimages in insertion order rather than JCS
* feature:Byte contracts: The system domain is a parameter, never a constant — every artifact takes its `system_id` from the signed evidence it was authorized under, and the two projections must agree before a submission set is assembled
* feature:Errors: An unsupported subject profile fails closed (`UnsupportedProfileError`) and the JSON-object profiles enforce their preconditions before canonicalizing (`SubjectPreconditionError`); neither ever falls back to another profile, and both types are exported so a caller can tell malformed input from transport failure without matching message text
* feature:Types: `SettlementWindowEstimate`, `SettlementProgress`, `WaitProgress`, `CommitmentInclusionProof`, `EmissionHandle` and `EmissionResolution` are exported, so a typed integration never needs `any` to describe something this SDK returns — including the nested `WaitProgress.settlement`, whose type is exported for the same reason as the object carrying it
* feature:Conformance: Byte parity against the published vectors, and SDK-minted certificates round-tripped through `certcrypt-verifier-toolkit-js` with every signature verified; both need sibling checkouts and fail with a message naming what to check out when one is absent (`CERTCRYPT_ALLOW_MISSING_CONFORMANCE=1` turns those failures back into skips)
* feature:Packaging: Requires Node.js 20 or newer. Server-side only — the issuer seed must never reach a browser bundle
